# Adoption wedge for agentic-go (2026-08-24)

## Executive conclusion

The best initial product is not an MCP server and not a selective-test
optimizer. It is a small, installable **Go pull-request verification report**:
given a base revision and a working tree, explain what changed, which packages
and checks are plausibly affected, what was actually run, and where the tool is
uncertain. Ship it first as a CLI with a GitHub Actions adapter; make MCP an
adapter for agents after the underlying result is useful to humans and CI.

This is an inference from the workflow and product boundaries below, not a
claim that a market has already been proven.

## What existing Go tooling already does

The standard toolchain already makes whole-repository verification easy and
machine-readable: `go test` supports package-list mode, caching, and JSON test
events, while `go vet` examines suspicious constructs. [Go command
documentation](https://go.dev/cmd/go/?m=old) [Go command
overview](https://go.dev/doc/cmd)

`gopls` already combines the usual `go vet` analyzers, additional analyzers,
Staticcheck analyzers, diagnostics, and safe code actions. [gopls
analyzers](https://go.dev/gopls/analyzers) [gopls transformations](https://go.dev/gopls/features/transformation)

`golangci-lint` is a configurable runner that parallelizes many linters,
supports caching, YAML configuration, and IDE integration. It therefore owns
the broad “run lots of static checks” position. [golangci-lint
README](https://github.com/golangci/golangci-lint)

`govulncheck` owns vulnerability identification from the Go vulnerability
database and should not be displaced by another generic security scanner.
The official documentation describes its source- and symbol-oriented analysis
and command-line usage. [govulncheck documentation](https://go.dev/doc/security/vuln)

**Implication:** adding more style, navigation, generic lint, or vulnerability
rules is weak differentiation. The gap is the relationship between a specific
change and a defensible verification decision.

## Repeated pain that remains available

The following are bounded gaps, not proof that every Go team experiences them:

1. **Reviewers cannot quickly see verification scope.** Existing commands say
   whether selected commands passed; they do not explain why a changed
   declaration implies checking a reverse importer, a test entry point, a race
   run, or a package-wide fallback.
2. **A green narrow check can be misleading.** Dependency and impact analysis
   can propose candidates, but Go's dynamic behavior, generated code, build
   tags, embedding, reflection, external systems, and test fixtures make
   sound selective execution difficult. The useful output is therefore a
   conservative plan plus explicit uncertainty, not “these omitted tests are
   safe.”
3. **Evidence is scattered.** `go test -json`, race output, vet/analyzer
   findings, package graph facts, and the diff are individually available but
   are rarely presented as one review artifact tied to the change.
4. **CI setup is repetitive but already standardized.** GitHub recommends
   `actions/setup-go`; the action resolves Go versions and caches modules/build
   outputs by default. [setup-go README](https://github.com/actions/setup-go)
   [GitHub Go workflow guide](https://docs.github.com/en/actions/tutorials/build-and-test-code/go)

The product opportunity is consequently an explanation/evidence layer and a
conservative planner around existing Go commands, not a replacement test
runner.

## Overlap and differentiation

There are already small open-source affected-test tools. For example,
`affected-tests` walks a dependency graph from changed files to test files and
explicitly warns that file-level analysis can create false positives.
[affected-tests README](https://github.com/cant89/affected-tests)

That overlap is a warning against leading with “run fewer tests.” The durable
boundary for agentic-go should be:

> **Change evidence and verification guidance for Go, with conservative
> execution and an honest account of uncertainty.**

Its output should answer, in order:

- What changed (files, packages, declarations, module/build metadata)?
- What could be affected, and what evidence supports each relationship?
- Which checks were selected, which were actually executed, and why?
- What was not checked, and what prevents a stronger conclusion?

Selective test execution can be an optional optimization only after measured
precision/recall evidence. It should never be the core correctness promise.

## Distribution and initial wedge

Successful Go developer-tool distribution has three useful properties:

- **One familiar command.** Go 1.24+ supports declaring tool dependencies in
  `go.mod` and invoking them with `go tool`, which reduces installation drift.
  [Go tool dependencies](https://go.dev/doc/modules/managing-dependencies)
- **CI-native installation and caching.** `setup-go` is the recommended GitHub
  Actions path and exposes version-file and cache controls. [GitHub Go workflow
  guide](https://docs.github.com/en/actions/tutorials/build-and-test-code/go)
- **Protocol adapters are downstream.** The official MCP Go SDK presents a
  server as a process connected over transports such as stdio; it does not
  define the domain workflow. [MCP Go SDK overview](https://go.sdk.modelcontextprotocol.io/)
  [MCP Go SDK quick start](https://go.sdk.modelcontextprotocol.io/quick_start/)

Therefore the adoption order should be:

1. `agentic-go verify --base origin/main` as a useful local command, with
   terminal and stable JSON output.
2. A thin GitHub Action that runs the same binary and emits a concise PR
   summary/annotations; no service, account, or MCP configuration required.
3. `go vet` integration for the high-confidence analyzers, where it naturally
   fits.
4. MCP `verify-change` exposing the same structured result to agents.

The CLI is the product seam, but CI is the first adoption wedge: a maintainer
can try it on one workflow, teammates see the result in a familiar PR, and
there is no editor-specific protocol or agent setup. Editor/MCP should follow
because their value depends on the result model already being trustworthy.

## Concrete v0.2 product recommendation

Call the product **change verification for Go**. Keep MCP out of the primary
headline.

Minimum valuable result:

- changed files/packages/declarations;
- affected packages and reverse-import evidence;
- selected checks and reason codes;
- actual `go test`, race, vet/analyzer evidence when run;
- explicit uncertainty for generated code, build constraints, embeds,
  reflection/dynamic calls, oversized graphs, and unsupported cases;
- terminal plus versioned JSON;
- exit status describing execution/result state, never universal safety.

Do not initially promise SARIF, Markdown, automatic test skipping, security
coverage, or dozens of MCP tools. Add each only when a real repository shows a
repeated need and the output contract can be evaluated.

Recommended README sentence:

> **agentic-go explains what a Go change may affect and what evidence you
> should collect before merging. Run it locally, in CI, or through MCP.**

The strongest proof-of-use metrics are not downloads or stars: successful
first-run rate, time to install, percentage of PRs with a useful report,
accepted findings, reviewer-confirmed false positives, runtime overhead, and
the fraction of reports that change the checks or review decision.
