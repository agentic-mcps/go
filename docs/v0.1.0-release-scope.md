# v0.1.0 Release Scope — canonical release authority

This document **supersedes** `decision-memo.md`'s "all 6 phases equally
mandatory" decision. The reasoning: a shipped 7-tool server that does
something no other Go MCP server does beats an unfinished 30-tool server
that exists only as a spec. Phase 4's audit tools are the thesis; everything
else is either a wrapper over existing tooling or a nice-to-have that can
follow once the thesis is proven in the wild.

### 1 standalone analyzer binary: `cmd/agentic-go-vet/` (detailed spec)

**Purpose.** The 2 custom `go/analysis` passes are this project's thesis.
Locking them behind MCP limits the audience to MCP client users. Exposing
them as a standard `go vet`-compatible CLI widens it to anyone who runs
`go vet`. A user who never installs an MCP client still gets the
concurrency and error-handling audit rules.

**Driver: `multichecker`, not `singlechecker`.** `singlechecker.Main` is
for single-analyzer CLI tools. `multichecker.Main` accepts multiple
analyzers and follows `go vet`'s output and exit-code conventions. The
`os.Exit` concern from contracts.md's `checker.Analyze` decision does not
apply here: this IS a CLI tool, `os.Exit` is correct for a CLI entry point.

**File: `cmd/agentic-go-vet/main.go`**

```go
package main

import (
    "github.com/ashwingopalsamy/agentic-go/internal/analysis/concurrency"
    "github.com/ashwingopalsamy/agentic-go/internal/analysis/errors"
    "golang.org/x/tools/go/analysis/multichecker"
)

func main() {
    multichecker.Main(concurrency.Analyzer, errors.Analyzer)
}
```

That is the entire binary. No flags, no config, no custom output formatting.
`multichecker.Main` handles:
- `packages.Load` with the correct `Need*` mode bits (it knows what the
  analyzers require via their `*analysis.Analyzer` metadata).
- Running all passed analyzers over all packages matching the user's
  pattern (`./...`, a specific import path, etc.).
- Printing diagnostics in `go vet`'s standard text format
  (`file:line:col: message`).
- Exit codes: `0` if clean, `3` if findings present, `1` on usage/analysis
  error. These match `go vet`'s own conventions.

**The `Analyzer` values are shared, not duplicated.** `concurrency.Analyzer`
and `errors.Analyzer` are the same `*analysis.Analyzer` structs the MCP
tools use via `audit.Run`. The binary is a different driver for the same
analyzers: `multichecker.Main` instead of `audit.Run` + `checker.Analyze`.
Both feed the same `run(pass *analysis.Pass)` functions. A rule fix in
`internal/analysis/concurrency/concurrency.go` lands in both the MCP tool
and the CLI binary with zero duplication.

**Install and usage.**

```bash
# Install
go install github.com/ashwingopalsamy/agentic-go/cmd/agentic-go-vet@latest

# Direct usage (like go vet)
agentic-go-vet ./...
agentic-go-vet ./internal/...

# As a vettool (lets `go vet` run it with go's own package loading)
go vet -vettool=$(which agentic-go-vet) ./...
```

The `-vettool` path is how `go vet` integrates third-party analyzers: `go
vet` loads packages itself, then calls the vettool binary as a subprocess
for each package. This is the standard integration path documented in
`go help vet`.

**Testing.** The analyzer logic is already tested exhaustively via
`astutil.RunFixture` in the per-domain tests
(`TestAuditConcurrency_RuleNN`, `TestAuditErrors_RuleNN`). The binary
itself is 7 lines of glue. One smoke test verifies the wiring:

```go
// cmd/agentic-go-vet/main_test.go
package main

import (
    "errors"
    "os/exec"
    "path/filepath"
    "strings"
    "testing"
)

// TestVetBinarySmoke builds the binary, runs it against a known fixture
// directory that contains a concurrency-01 violation, and asserts:
// - exit code is 3 (findings present, per go vet convention)
// - combined output contains "concurrency-01"
// This is a wiring test (import paths resolve, analyzers registered),
// not a logic test (logic is covered by per-domain fixture tests).
func TestVetBinarySmoke(t *testing.T) {
    repoRoot := filepath.Join("..", "..")
    binPath := filepath.Join(t.TempDir(), "agentic-go-vet")
    cmd := exec.Command("go", "build", "-o", binPath, "./cmd/agentic-go-vet")
    cmd.Dir = repoRoot
    if output, err := cmd.CombinedOutput(); err != nil {
        t.Fatalf("build agentic-go-vet: %v\n%s", err, output)
    }

    // Run against a fixture known to trigger concurrency-01
    // (reuse the existing audit-concurrency/rule01 fixture)
    cmd = exec.Command(binPath, "./internal/tools/testdata/fixtures/audit-concurrency/rule01/...")
    cmd.Dir = repoRoot
    output, err := cmd.CombinedOutput()
    var exitErr *exec.ExitError
    if !errors.As(err, &exitErr) || exitErr.ExitCode() != 3 {
        t.Fatalf("expected findings exit code 3, got %v\n%s", err, output)
    }
    if !strings.Contains(string(output), "concurrency-01") {
        t.Fatalf("missing concurrency-01 diagnostic:\n%s", output)
    }
}
```

This is the one test that would fail if the import paths broke or an
analyzer wasn't registered. It does not re-test predicate logic.

### `verify-change` prompt (new, not in existing spec) — detailed spec

**Purpose.** The most common AI coding workflow is "I just changed this
function, verify the change is safe." This is a high-frequency loop
repeated dozens of times per session. None of the existing prompts target
it:
- `pre-commit-check` includes coverage (slow, not run after every edit) and
  has a coverage threshold gate.
- `audit-package` runs full audit but omits tests and race detection.
- `bisect-flake` targets a specific flake investigation, not general
  verification.

`verify-change` is the lightweight, repeat-50-times-during-a-session
version: tests + race + 2 audits, no coverage, no benchmark.

**Registration.** `internal/tools/prompts.go`, alongside the other 3
v0.1.0 prompts. Same `server.AddPrompt` pattern as `phase-3-gopls-navigation-resources-prompts.md`:

```go
func RegisterVerifyChangePrompt(server *mcp.Server) {
    server.AddPrompt(&mcp.Prompt{
        Name:        "verify-change",
        Description: "Post-edit verification: run tests with race detector and concurrency+error audits against a package. Lightweight, no coverage. Repeat after every edit.",
        Arguments: []*mcp.PromptArgument{
            {Name: "package", Description: "Go package import path or ./relative/path", Required: true},
        },
    }, func(ctx context.Context, req *mcp.GetPromptRequest) (*mcp.GetPromptResult, error) {
        pkg := req.Params.Arguments["package"]
        var buf bytes.Buffer
        if err := verifyChangeTmpl.Execute(&buf, map[string]string{"package": pkg}); err != nil {
            return nil, fmt.Errorf("rendering verify-change prompt: %w", err)
        }
        return &mcp.GetPromptResult{
            Messages: []*mcp.PromptMessage{{
                Role:    "user",
                Content: &mcp.TextContent{Text: buf.String()},
            }},
        }, nil
    })
}

var verifyChangeTmpl = template.Must(template.New("verify-change").Parse(`You are verifying a recent edit to the Go package {{.package}}. Run these tools in sequence and report findings:
1. Call go_test_structured with package="{{.package}}" and race=true. Report:
   - Any test failures: list each by name.
   - Any race conflicts: list each by location (file:line) and the two goroutines involved.
   - If all tests pass and no races: state "tests pass, no races detected."

2. Call go_audit_concurrency with package="{{.package}}". Report:
   - Any findings: list each as [severity] rule-id at file:line — message.
   - If zero findings: state "no concurrency findings."

3. Call go_audit_errors with package="{{.package}}". Report:
   - Any findings: list each as [severity] rule-id at file:line — message.
   - If zero findings: state "no error-handling findings."

Final line: if all three steps are clean, state explicitly "no issues found in {{.package}}." If any step reported issues, state "issues found in {{.package}}: N test failures, M race conflicts, C concurrency findings, E error-handling findings."

Do not omit the negative result. A clean result is a real, reportable outcome, not a non-answer. Coverage is intentionally omitted — it is too slow for a per-edit verification loop.`))
}
```

`main.go` calls `RegisterVerifyChangePrompt(server)` alongside the other
3 prompt registrations. Same flat-list pattern as tool registration.

**Why a prompt, not a tool.** This could be a tool (`go_verify_change`)
that internally calls all three and merges results. It's a prompt instead
for two reasons:
1. The individual tools (`go_test_structured`, `go_audit_concurrency`,
   `go_audit_errors`) already exist and are composable. A wrapper tool
   would re-implement their orchestration, duplicating `audit.Run`'s
   existing orchestration for the audit pair and adding a test-runner
   merge layer, all for a fixed sequence a prompt template expresses in 20
   lines of text.
2. A prompt lets the calling agent adapt: skip a step if the edit didn't
   touch concurrency-sensitive code, add `go_coverage_gaps` if the edit is
   large, re-run just the failing test. A tool with a fixed internal
   sequence can't adapt. The prompt is the lightweight contract; the agent
   is the orchestrator.

**What it omits and why.**
- **Coverage** (`go_coverage_gaps`): adds ~5-30s per call depending on
  package size. A per-edit loop run 50 times per session adds minutes of
  cumulative wait for data that's only actionable at commit time. Coverage
  belongs in `pre-commit-check`, not here.
- **Benchmark** (`go_benchmark_diff`): requires a git worktree and a
  baseline. Not a per-edit concern.
- **Flake finder** (`go_flake_finder`): requires `count=N` repeated runs.
  Not a per-edit concern.
- **Other audit domains** (security, observability, naming, type design,
  performance): not in v0.1.0.

**Verification.** One test in `internal/tools/prompts_test.go`:
```go
func TestVerifyChangePrompt_Renders(t *testing.T) {
    // Call the prompt handler with package="./internal/parser"
    // Assert the returned message contains all 3 tool-call instructions
    // Assert it contains {{.package}} substituted, not the literal template
    // Assert it contains "no issues found" as the clean-state instruction
}
```
This is a template-rendering test, not a tool-execution test. The tools
themselves are tested by their own per-tool test suites. The prompt's
contract is "renders the correct instruction sequence with the argument
substituted," nothing more.

## False-positive validation before tagging v0.1.0 (detailed spec)

**Purpose.** The #1 adoption killer for static analysis is noise. A tool
that fires on common, correct code gets uninstalled or ignored. A tool with
a low false-positive rate and a published number is a marketing asset no
competitor has. This step runs before tagging v0.1.0, not after.

### Process

**Step 1: Prepare at least ten prominent OSS Go projects.** The user clones
the agreed repositories locally after the implementation is otherwise
complete. Record an immutable commit hash and exact scanned package pattern
for every project before analysis; the validation process does not fetch or
update repositories. Candidate list (high LOC, well-maintained, diverse code
styles):

| Project | Import path | Why included |
|---|---|---|
| `spf13/cobra` | `github.com/spf13/cobra` | CLI framework, widely used, idiomatic Go |
| `gin-gonic/gin` | `github.com/gin-gonic/gin` | HTTP framework, concurrency-heavy |
| `labstack/echo` | `github.com/labstack/echo` | HTTP framework, different style from gin |
| `stretchr/testify` | `github.com/stretchr/testify` | test framework, mock-heavy |
| `go-chi/chi` | `github.com/go-chi/chi` | HTTP router, minimal style |
| `grpc/grpc-go` | `google.golang.org/grpc` | gRPC, complex concurrency, channel patterns |
| `prometheus/client_golang` | `github.com/prometheus/client_golang` | metrics, concurrency, atomic patterns |
| `golang/go` (stdlib subset) | `cmd/`, `net/http`, `sync/` | gold standard, should be near-zero findings |
| `hashicorp/vault` | `github.com/hashicorp/vault` | large codebase, production-grade concurrency |
| `kubernetes/client-go` (subset) | `k8s.io/client-go/...` | largest Go codebase, stress test for noise |

The user chooses the parent directory and supplies its path. Repository
checkouts are never committed to agentic-go.

**Step 2: Run `agentic-go-vet ./...` against each.** The binary makes this
trivial. Script:

```bash
#!/bin/bash
# validation/run-fp-check.sh
set -euo pipefail

PROJECTS_DIR="${1:-/tmp/fp-validation}"
RESULTS_DIR="validation/v0.1.0/findings"
mkdir -p "$RESULTS_DIR"

for proj_dir in "$PROJECTS_DIR"/*/; do
    proj=$(basename "$proj_dir")
    echo "=== $proj ==="
    cd "$proj_dir"
    agentic-go-vet ./... 2>&1 | tee "$RESULTS_DIR/$proj-findings.txt" || true
    cd - >/dev/null
done
echo "Done. Raw output in $RESULTS_DIR/"
```

`|| true` on the `agentic-go-vet` line because exit code 3 (findings
present) would otherwise abort the script under `set -e`.

**Step 3: Classify each finding.** For every finding, assign one of three
labels:

| Label | Definition |
|---|---|
| True positive | The code is genuinely wrong or risky per the rule's source reference. A human reviewer would flag it. |
| False positive | The code is correct. The rule's predicate is too broad, or the pattern has a safe variant the analyzer doesn't recognize. |
| Style preference | The code is correct, the rule's guidance is debatable, and reasonable engineers would disagree. Not a bug, not noise — a judgment call the rule shouldn't force. |

Record in a CSV (`validation/v0.1.0/results.csv`):

```csv
project,rule,severity,file,line,message,label,notes
cobra,concurrency-01,error,foo.go:42,goroutine without owner,false-positive,spawned in errgroup .Go() not recognized
gin,concurrency-06,warning,bar.go:88,context.Background() in goroutine,true-positive,genuinely orphaned
```

**Step 4: Calculate metrics.**

```
LOC per project:     find . -name '*.go' -not -path '*/vendor/*' | xargs wc -l | tail -1
Findings per 1k LOC: total_findings / (total_LOC / 1000)
FP rate (aggregate): false_positives / total_findings
FP rate (per-rule):  group by rule ID, false_positives_in_rule / findings_in_rule
```

A `Makefile` target or small Go script automates the counting from the CSV.

**Step 5: Act on results.**

- **A rule with >5% FP rate across projects, or systemic false positives:**
  disable the rule for v0.1.0 and fix it before enabling it again. This is a
  release gate, not a documentation task.
- **A rule with >50% FP rate across projects:** fix the predicate before
  release. This is a bug list, not a documentation task. Re-run validation
  after the fix. A rule firing at >50% FP is actively harmful — users will
  add `//nolint` suppressions that mask real future violations.
- **A rule with <20% FP rate:** ship it. If the rate is very low (<5%),
  mention it in the README per-rule.
- **A rule that's mostly "style preference":** consider downgrading
  severity (`error`→`warning`, `warning`→`info`) or moving to the excluded
  list with a documented reason. Style-preference rules at `SeverityError`
  are the fastest way to get uninstalled.

**Step 6: Publish in README if the aggregate FP rate is low.**

If the overall false-positive rate is <15% across all projects, add this
section to `README.md`:

```markdown
## Validation

`agentic-go-vet` was validated against N popular Go projects
(cobra, gin, echo, testify, chi, grpc-go, ...).

| Metric | Value |
|---|---|
| Total LOC scanned | X |
| Total findings | Y |
| Findings per 1000 LOC | Z |
| False-positive rate | W% |

Per-rule false-positive rates: see `validation/v0.1.0/results.csv` in the
release source tree.
```

If the rate is >=15%, do not publish a number. Fix the noisy rules first.
A published high FP rate is worse than no number — it advertises the
problem.

This is reproducible evidence, not a marketing claim. A skeptical user can

### When to run

After the analyzers pass their own per-rule fixture tests (build sequence
step 3) and after `cmd/agentic-go-vet` is built and self-hosting (step 4),
before Phase 6 docs (step 6). The README references the validation results,
so validation must complete first. This is build sequence step 7, before
the tag (step 8).

### Not a one-time exercise

Re-run on every minor release (v0.2.0, v0.3.0) as new rules are added. The
`validation/` directory accumulates per-release results, making FP-rate
trends visible. A rule that was clean in v0.1.0 but noisy after a predicate
change in v0.2.0 is caught by the trend, not by a user filing a bug.
