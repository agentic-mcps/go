# Feedback on the v0.1.0 MCP Self-Test

I connected Codex to agentic-go through an ephemeral local stdio MCP
configuration and ran the server against the repository itself. The
integration worked end to end: four resources and seven tools were discovered,
the module reported Go 1.25, and the repository contained 15 packages and 11
active analyzer rules. Both audit passes scanned 60 files and returned zero
findings. Structured testing executed 115 passing tests with zero failures.

The trust boundary also behaved as intended. Execution was initially gated by
the trust annotations under a no-approval policy and proceeded only after
approval-review mode allowed it. The session left no persistent Codex MCP
configuration, no server running, and no worktree changes. That is good
evidence that the local-only connection is usable without quietly expanding
the repository or host state.

## The toolchain failure was real, but recoverable

The first connection inherited Go 1.24.2 with `GOTOOLCHAIN=local`. The server
started, but package loading failed because this repository requires Go 1.25.
Pinning Go 1.27 in the MCP process environment made the same connection work.
This is an ergonomics and startup-preflight problem, not evidence that the MCP
surface is fundamentally unreliable. A client should either receive clear
guidance about the effective Go toolchain and `PATH`, or the server should
fail early with a direct version diagnostic rather than presenting a vague
loading failure.

## A core structured-test status bug blocks tagging

The successful test run exposed a correctness defect in the structured result
contract. `cmd/agentic-go` and `internal/progress` have no test files. The
underlying Go test command succeeds, but package-level `skip` events are
currently labeled `FAIL` by the structured adapter. The relevant handling is
in [`internal/tools/go_test_structured.go`](../../internal/tools/go_test_structured.go),
where package events are mapped; a no-test package must not be reported as a
failed package.

This is more serious than presentation polish. An agent consuming the
structured result can make the wrong release or remediation decision even when
the repository tests passed. The status mapping should be corrected and
covered before tagging v0.1.0.

## Response shape needs a bounded default

Although the test request used `verbose=false`, returning all 115 successful
test cases still produced a large MCP response. The data is useful, but the
default is not context-efficient for an agent that primarily needs to decide
whether to investigate a failure.

The better default is an aggregate result with package summaries, failures,
and skips; complete passing-test detail should be opt-in. This would preserve
diagnostic depth while reducing context pressure and making the important
signals more prominent.

## Assessment

The local MCP integration works and the containment and trust behavior held up
under direct dogfooding. The evidence also found a release-blocking status bug,
so I would not tag v0.1.0 until package-level skips are represented correctly.
After that, improve toolchain detection and configuration ergonomics, then
revisit the default structured response size. These are focused fixes to an
otherwise credible integration boundary, not a reason to broaden the product
surface prematurely.

## Follow-up: 2026-08-24 remediation

The release blockers above were corrected and the local stdio dogfood was
repeated with Go 1.27 pinned in the MCP process environment. Codex discovered
seven tools and read all four resources. The workspace resource reported 15
packages, the dependency resource reported 11 modules, the rules resource
reported 11 active rules, and the trace summary remained disabled and empty.

Both repository-wide audits completed without findings or truncation after
scanning 60 files each. Because the repository produced no audit findings,
there were no location values in this run to render; workspace-relative
location normalization remains exercised by the automated tool tests.

`go_test_structured` completed with 139 passing tests, zero failed tests, and
zero skipped test cases. Thirteen packages reported `ok`. The two packages
without tests, `cmd/agentic-go` and `internal/progress`, reported `skip` rather
than `FAIL`, while the skipped-test aggregate remained zero. The complete
per-test list was still returned with `verbose=false`, preserving the v0.1
response contract.

Startup now preflights the `go` executable inherited through the MCP process
`PATH` with `GOTOOLCHAIN=local`, and it rejects an unusable or too-old
toolchain before workspace loading. It also rejects a toolchain older than the
highest Go version required by the active workspace modules. Explicit support
remains Go 1.25 through Go 1.27; passing a future toolchain preflight does not
claim support for it.

The remediation run retained approval gating for executable tools. It left no
persistent agentic-go MCP configuration, no server process, and no worktree
changes. A summary/detail control for large structured-test responses remains
a deliberate v0.2 follow-up; v0.1 does not silently remove successful test
records.
