# v0.2.0 release scope — change-aware verification

This document is the canonical implementation authority for v0.2.0. The
tagged [`v0.1.0 release scope`](v0.1.0-release-scope.md) remains the
compatibility baseline. When this document conflicts with a broader roadmap,
this document wins for v0.2.0.

## Product thesis

v0.2.0 turns a working-tree change into a compiler-grounded, explainable
verification plan.

A frontier coding model can already read a diff and guess which tests to run.
The useful product boundary is narrower and harder: combine the actual Git
change, Go package graph, declarations, static call relationships, and test
entry points; then return the smallest defensible verification plan together
with the evidence and uncertainty behind it.

Agentic-go remains an instrument for an external coding agent. It does not
embed an LLM, choose whether a change is correct, edit source, or become an
agent framework.

## Release inventory

The v0.2.0 target is exactly:

- eight MCP tools;
- four MCP resources;
- four MCP prompts;
- the `agentic-go-vet` binary; and
- stdio transport only.

The only new public tool is `go_change_impact`. The seven v0.1.0 tools, four
resources, four prompts, and CLI remain available. Until implementation and
the registry gate are complete, the live server still exposes the v0.1.0
inventory; documentation must not claim otherwise.

No analyzer rule is added and no existing detection predicate changes in this
release.

## Flagship tool: `go_change_impact`

### Contract

`go_change_impact` inspects local changes relative to a local Git commit,
relates changed Go declarations to packages and tests, and returns an ordered
plan expressed as calls to existing agentic-go tools. It does not execute the
plan.

```go
type ChangeImpactInput struct {
    Base        string `json:"base,omitempty"`
    Package     string `json:"package,omitempty"`
    MaxChanges  int    `json:"max_changes,omitempty"`
    MaxPackages int    `json:"max_packages,omitempty"`
    MaxTests    int    `json:"max_tests,omitempty"`
}
```

Defaults and bounds:

| Field | Default | Contract |
|---|---:|---|
| `base` | `HEAD` | Local commit-ish resolved to a commit; no fetch or network access |
| `package` | `./...` | Go package pattern contained by the configured workspace |
| `max_changes` | `500` | Minimum 1, maximum 2,000; fail if the narrowed change set is larger |
| `max_packages` | `200` | Minimum 1, maximum 500; fail if the selected package graph is larger |
| `max_tests` | `200` | Minimum 1, maximum 500; broaden to package-level verification if exceeded |

The advertised JSON schema carries these defaults. Runtime normalization is
authoritative when a client omits them.

```go
type ChangeKind string // added | modified | deleted | renamed | untracked
type SymbolKind string // func | method | type | var | const | field
type Confidence string // high | medium | low

type LineRange struct {
    Start int `json:"start"`
    End   int `json:"end"`
}

type ChangedFile struct {
    Path          string      `json:"path"`
    PreviousPath  string      `json:"previous_path,omitempty"`
    Change        ChangeKind  `json:"change"`
    BaseRanges    []LineRange `json:"base_ranges"`
    CurrentRanges []LineRange `json:"current_ranges"`
}

type ChangedSymbol struct {
    Package         string            `json:"package"`
    Name            string            `json:"name"`
    Kind            SymbolKind        `json:"kind"`
    Change          ChangeKind        `json:"change"`
    BaseLocation    *finding.Location `json:"base_location,omitempty"`
    CurrentLocation *finding.Location `json:"current_location,omitempty"`
}

type AffectedPackage struct {
    ImportPath string     `json:"import_path"`
    Reasons    []string   `json:"reasons"` // changed | reverse_import | test_reachable | fallback
    Distance   int        `json:"distance"`
    Confidence Confidence `json:"confidence"`
}

type ImpactEvidence struct {
    Kind     string            `json:"kind"`
    Source   string            `json:"source"`
    Target   string            `json:"target,omitempty"`
    Location *finding.Location `json:"location,omitempty"`
    Detail   string            `json:"detail"`
}

type VerificationArguments struct {
    Package   string `json:"package"`
    TestRegex string `json:"test_regex,omitempty"`
    Detail    string `json:"detail,omitempty"`
}

type VerificationStep struct {
    Tool       string                `json:"tool"`
    Arguments  VerificationArguments `json:"arguments"`
    Reason     string                `json:"reason"`
    Confidence Confidence            `json:"confidence"`
    Evidence   []ImpactEvidence      `json:"evidence"`
}

type ImpactUncertainty struct {
    Code      string             `json:"code"`
    Message   string             `json:"message"`
    Locations []finding.Location `json:"locations"`
}

type ChangeImpactOutput struct {
    BaseCommit       string              `json:"base_commit"`
    HeadCommit       string              `json:"head_commit"`
    ChangedFiles     []ChangedFile       `json:"changed_files"`
    ChangedSymbols   []ChangedSymbol     `json:"changed_symbols"`
    AffectedPackages []AffectedPackage   `json:"affected_packages"`
    VerificationPlan []VerificationStep  `json:"verification_plan"`
    Uncertainties    []ImpactUncertainty `json:"uncertainties"`
}
```

The production declarations may be formatted differently, but field names,
wire meanings, enumerations, and initialization guarantees above are the
contract. Every collection is non-nil on a clean result. `base_commit` and
`head_commit` are full object IDs. `head_commit` identifies the current
`HEAD`; `changed_files` represents the combined final working-tree snapshot,
including staged and unstaged content, and does not imply those changes are
committed.

`base_ranges` refers to lines in the base tree; `current_ranges` refers to the
final working-tree snapshot. A deleted file has no current ranges and an
untracked file has no base ranges. A rename, including a rename with content
changes, uses `change="renamed"`, sets `previous_path`, and carries both sides'
ranges when content changed. A deleted symbol has only `base_location`; an
added or untracked symbol has only `current_location`; a retained or renamed
symbol may have both. At least one symbol location is always present.

An unchanged workspace is a successful result with commit IDs and empty
collections. Protocol, Git, package-loading, parsing, cancellation, deadline,
and containment failures return errors rather than a partial clean result.

### Tool annotations

`go_change_impact` is:

- read-only: `true`;
- destructive: `false`;
- idempotent: `true` for the same repository state; and
- open-world: `false`.

It reads Git and Go source metadata inside the configured workspace. It does
not compile or execute target code, mutate Git state, create a worktree, write
artifacts, or use the network.

### Repository and containment behavior

1. Resolve `base` with Git's end-of-options protection and peel it to a local
   commit. Reject a missing, ambiguous, non-commit, or option-like value.
2. Resolve the repository top level and require it to contain the configured,
   symlink-resolved workspace. A workspace nested inside a larger repository
   is valid; changes outside the configured workspace are excluded.
3. Treat the final working tree as one snapshot. Compare the base tree directly
   with that snapshot using `git diff --find-renames --raw -z` and a matching
   zero-context patch. This single comparison includes committed changes after
   `base`, staged changes, and unstaged tracked changes without merging three
   competing diffs. Read untracked, non-ignored paths separately with
   `git ls-files --others --exclude-standard -z`, then add one `untracked`
   record per path. A tracked path wins if malformed Git state reports the
   same final path twice. The tool reports final content impact, not staging
   provenance. Never fetch a ref, invoke a shell, or parse locale-dependent
   human output.
4. Convert every reported path to a slash-separated workspace-relative path.
   Reject path traversal and any resolved path outside the workspace.
5. Ignore non-Go files for declaration and call analysis, but retain them in
   `changed_files` when they can affect Go behavior, including `go.mod`,
   `go.sum`, `go.work`, `go.work.sum`, and files named by the active build's
   `EmbedFiles` or `TestEmbedFiles` from `go list -json`. Do not reimplement
   embed pattern matching. Such changes require explicit package-level
   fallback evidence.
6. Apply the package scope before enforcing `max_changes`. Fail with the
   observed count and a narrowing instruction rather than returning an
   arbitrary prefix.

With the default `package="./..."`, enumerate `./...` independently from each
active module root in `go.work`, or from the containing module when no work
file is active, and union the results. An explicit package pattern defines the
analysis universe. `go.mod` and `go.sum` changes affect every selected package
in their module; `go.work` and `go.work.sum` changes affect every selected
package in the active workspace. If current module metadata cannot be loaded,
the tool fails rather than presenting a partial plan as clean.

Changed generated files are analyzed when present but always produce a
`generated_code` uncertainty. The tool never runs generators.

### Analysis pipeline

The implementation performs one bounded analysis pass:

1. Extend the existing workspace-contained `go list` selection pass to collect
   active compiled and test files. Fail rather than silently truncate when
   more than `max_packages` packages are selected. Before syntax loading, cap
   the file count and the combined byte size of current compiled source plus
   base versions of changed Go files.
2. Load the selected packages and their tests once with the syntax, type,
   import, and module information required by the analysis. Reserve the shared
   runner permit for this in-process work and force `GOPROXY=off`, `GOSUMDB=off`,
   and `GOTOOLCHAIN=local`. Package load errors fail the call with the affected
   package named. Count declarations from the loaded syntax before SSA.
3. Parse old and current files as needed to identify added, modified, deleted,
   and renamed declarations intersecting changed hunks. A declaration is not
   marked changed merely because its file changed elsewhere.
4. Build the reverse import graph. A changed package is high confidence;
   direct and transitive import dependents are candidates with their minimum
   import distance recorded.
5. Build SSA and static call relationships for the bounded package set.
   Direct calls and statically resolved method calls are high-confidence
   evidence. Interface-call candidates may use bounded VTA refinement, remain
   conservative, and are never described as exact runtime reachability. If
   the refinement cannot honor the graph limits, emit interface uncertainty
   and use package-level fallback instead.
6. Invert test reachability: begin at top-level `Test*`, `Fuzz*`, and `Example*`
   entry points and associate reachable changed declarations with those entry
   points. Benchmarks are not selected because the existing execution tools do
   not provide a general `-bench` contract. Keep this map internal; v0.2.0 does
   not expose the deferred `go_test_map` tool.
7. Emit selected test steps when the evidence is specific. Emit whole-package
   fallback steps when deleted declarations, dynamic dispatch, graph gaps, or
   other uncertainty makes a narrower selection unsafe.
8. Sort files, symbols, packages, evidence, uncertainties, and verification
   steps deterministically. Equivalent repository state must produce
   byte-stable structured content apart from trace timing.

If more than `max_tests` test entry points are candidates, do not return an
arbitrary prefix. Replace test-specific steps with whole-package steps and add
`test_selection_limit` uncertainty explaining the broadening.

### In-process analysis bounds

The package and subprocess bounds are not sufficient for an SSA graph. Before
building it, enforce all of these fixed v0.2 limits across the selected active
build:

- 10,000 compiled or changed-base Go files;
- 64 MiB combined current and changed-base Go source;
- 100,000 declared functions and methods; and
- 500,000 retained call-graph edges.

Count files and bytes before full syntax loading, and declarations before SSA
construction. Produce call relationships incrementally; do not invoke a graph
API that must materialize an unbounded whole-program result before these limits
can be enforced. Check the request context between packages and during node
and edge traversal; visit each retained node and edge at most once. If a
source, function, or edge limit is reached, stop static reachability, preserve
the already-known changed and reverse-import packages, replace test-specific
steps with package-wide steps, and emit `analysis_limit` uncertainty. Never
return a partially traversed graph as if it were complete. Cancellation or
deadline remains a tool error.

### Evidence and confidence

Confidence states how directly the static evidence supports inclusion in the
plan; it is not a probability and never proves that omitted code is safe.

- `high`: the package changed directly, or a test has a direct/static call
  path to a changed declaration;
- `medium`: the relationship uses a reverse-import path or a conservative
  interface-call candidate; and
- `low`: the step is a safety fallback caused by incomplete static evidence.

Every verification step carries at least one evidence item. Evidence kinds
are stable strings:

- `changed_declaration`;
- `direct_call`;
- `transitive_call`;
- `interface_candidate`;
- `reverse_import`;
- `module_metadata`; and
- `package_fallback`.

`source` and `target` use typed stable identifiers: `file:<workspace-path>`,
`package:<import-path>`, `symbol:<import-path>.<qualified-name>`, or
`test:<import-path>.<top-level-name>`. `detail` is explanatory prose and is
not an identifier.

The first implementation must emit explicit uncertainty for every finite
signal below that it cannot model precisely. Stable uncertainty codes are:

- `interface_dispatch`;
- `reflection`;
- `generated_code`;
- `build_constraints`;
- `deleted_symbol`;
- `renamed_symbol`;
- `cgo_boundary`;
- `module_metadata`;
- `test_selection_limit`;
- `analysis_limit`;
- `unresolved_reachability`.

Unknown dynamic behavior broadens verification; it never narrows it.

Uncertainty detection is deliberately finite and does not claim to discover
all dynamic behavior:

| Code | Emitted when an affected package contains |
|---|---|
| `interface_dispatch` | an SSA invoke edge participating in candidate reachability |
| `reflection` | an import of `reflect` and a call to `reflect.Value.Call`, `CallSlice`, or `MakeFunc` |
| `generated_code` | a changed generated-file header or an active `go:generate` directive in the changed package |
| `build_constraints` | ignored Go files or affected files with `//go:build`/legacy build constraints |
| `deleted_symbol` | a declaration present only in the base tree |
| `renamed_symbol` | a declaration whose file or qualified name changed |
| `cgo_boundary` | active cgo files or an import of `C` |
| `module_metadata` | relevant `go.mod`, `go.sum`, `go.work`, or `go.work.sum` changes |
| `analysis_limit` | a fixed source, function, or graph-edge limit was reached |
| `unresolved_reachability` | a changed declaration has no retained static path to a test |

Plugins, assembly behavior, external processes, data-dependent registration,
and generated-at-build source absent from disk are documented limitations, not
claimed detections. Their existence cannot generally be inferred reliably
from a bounded static pass.

### Verification-plan composition

The plan uses only existing execution and audit tools. `tool` is one of the
four names below, and `arguments` is ready to pass to that tool:

- `go_test_structured` for selected or package-wide tests, always with
  `detail="nonpassing"`;
- `go_race_report` for the same selected or package-wide tests when Go code
  changed;
- `go_audit_concurrency` for directly changed Go packages; and
- `go_audit_errors` for directly changed Go packages.

The tool does not claim that these checks are exhaustive. It provides a
defensible starting plan that an external agent can broaden based on the
returned uncertainty, the nature of the edit, and project-specific commands.
All unspecified tool inputs use the target tool's advertised defaults. The
plan is ordered by affected-package distance, then package import path, then
tool priority: structured tests, race report, concurrency audit, error audit.

## Targeted test execution

`go_test_structured` and `go_race_report` each gain the same optional input:

```go
TestRegex string `json:"test_regex,omitempty"`
```

The value is a Go regular expression passed as the argument to `go test
-run`. Empty means all tests. Validation compiles the expression before any
subprocess starts, rejects NUL or leading-option forms, and limits the UTF-8
input to 4,096 bytes.

`go_change_impact` generates exact-name selections as an anchored expression,
sorting names and applying `regexp.QuoteMeta` to every entry. If the expression
would exceed 4,096 bytes, the plan uses a package-wide step and records
`test_selection_limit` uncertainty.

Impact-selected names are top-level tests, examples, or fuzz targets, never
dynamic subtest names. Go applies `-run` per slash-separated name component;
matching an anchored top-level name intentionally runs its descendants. A
caller-supplied regex retains Go's native hierarchical semantics.

Both tools construct arguments without a shell. `go_test_structured` uses
`go test -json -timeout <duration>` followed by optional `-race`, `-v`, and
`-run <regex>`, then the package pattern. `go_race_report` uses
`go test -race -json -timeout <duration>`, optional `-run <regex>`, then the
package pattern. Package init and selected test failures remain part of the
structured run; they are findings, not protocol errors. A selected name that
produces no terminal test record causes the prompt to rerun that package
without `test_regex` and report the broadened result.

This addition does not change tool annotations: both tools still execute
trusted repository code and remain potentially destructive, non-idempotent,
and open-world.

## Structured-test response detail

`go_test_structured` gains:

```go
Detail string `json:"detail,omitempty"` // summary | nonpassing | all
```

The default is `nonpassing`.

| Value | `tests` content |
|---|---|
| `summary` | Empty |
| `nonpassing` | Failed and skipped test cases |
| `all` | Every terminal test record, preserving v0.1.0 behavior |

The output adds:

```go
Detail       string `json:"detail"`
TestsOmitted int    `json:"tests_omitted"`
```

Package summaries and aggregate pass/fail/skip counts always cover the full
run. Failure output is preserved. `verbose` continues to control whether
passing and skipped output text is retained; it does not control which test
records qualify for the selected detail mode. Filtering happens only after
the complete event stream has been collected.

This intentional default change is called out in release notes. Clients that
need the complete v0.1.0 list set `detail="all"`.

## Explainable analyzer findings

The active rules behind `go_audit_concurrency` and `go_audit_errors` gain
bounded, structured context without changing predicates or finding identity.

```go
type RuleContext struct {
    Rule                 string   `json:"rule"`
    WhyItMatters         string   `json:"why_it_matters"`
    Remediation          string   `json:"remediation"`
    Limitations          []string `json:"limitations"`
    SourceDocument       string   `json:"source_document"`
    ValidationProvenance string   `json:"validation_provenance"`
}
```

`finding.AuditResult` gains `rule_context []RuleContext`. It contains one
entry per rule represented in the returned findings, sorted by rule ID, and
does not include unrelated or disabled rules. A clean result returns a non-nil
empty list.

`agentic-go://analysis-rules` exposes the same context for every active rule,
including active rules with no finding in a particular audit. Disabled rules
remain absent. `validation_provenance` describes the evidence actually held;
fixture coverage is not presented as external validation, and rules without
meaningful external hits are not marketed as validated.

## `verify-change` prompt

The prompt becomes a change-aware workflow and no longer requires a package
argument.

1. Call `go_change_impact` with its defaults.
2. Explain the changed files, selected tests/packages, evidence, confidence,
   and every uncertainty before executing checks.
3. Execute each ordered verification step with its specified package and
   typed arguments.
4. Use `go_race_report` for structured race conflicts. Do not ask
   `go_test_structured` to report race-conflict objects.
5. Broaden selected tests to the affected package, and then to the user-scope
   package pattern, when an uncertainty says the narrower plan is unsafe.
6. Report clean outcomes as explicitly as failures. Distinguish tool failure
   from a test or audit finding.

Execute all independent steps even when an earlier step reports test failures,
race conflicts, or audit findings. A no-test package is a valid `skip` result
and does not suppress its audits. On a tool error, report it and continue with
independent steps unless the request was cancelled, its deadline expired, or
the error makes the remaining package steps impossible.

The prompt composes tools; it does not hide calls, mutate files, or claim that
the plan proves correctness.

## Implementation boundaries

The intended seams are:

- `internal/changeimpact/` for Git parsing, declaration mapping, graph
  construction, test reachability, plan construction, and public data types;
- `internal/tools/go_change_impact.go` for MCP schema, normalization,
  annotations, progress, tracing, and runtime integration;
- the existing execution runner for cancellation, deadlines, concurrency,
  environment, and output caps;
- the existing workspace resolver for containment;
- `internal/tools.RegisterAll` as the one live inventory; and
- existing analyzer rule metadata as the single source for both audit results
  and the analysis-rules resource.

Use `golang.org/x/tools` already pinned by the repository. Add no production
dependency unless repository evidence proves the existing toolchain cannot
meet this contract.

The impact engine must not import MCP packages. The MCP adapter must not own
Git parsing or graph algorithms.

## Failure modes and trust boundary

- Dirty worktrees and untracked Go files are normal input.
- A missing Git repository, invalid base, package-load failure, malformed diff,
  exceeded package bound, cancellation, or deadline is a tool error.
- Build tags describe only the active toolchain configuration. Alternate tag,
  platform, and cgo paths are uncertainty, not silently analyzed claims.
- Static call graphs over-approximate some interface paths and under-model
  reflection, generated-at-build code, plugins, assembly, and external process
  behavior. The response says so when those mechanisms are detected.
- Workspace containment, bounded subprocesses, and closed-world analysis are
  controls, not a sandbox. The impact tool does not execute target code; the
  verification tools it recommends may do so.
- No response is described as proof that a change is safe or complete.

## Focused acceptance contract

v0.2.0 requires focused engineering verification, not a research program.

### Contract and fixture coverage

- Git change parsing covers staged, unstaged, untracked, added, modified,
  deleted, and renamed files, including a workspace nested in a repository.
- Declaration mapping covers functions, methods, types, variables, constants,
  fields, changes outside declarations, and deleted declarations.
- Package impact covers direct changes, reverse imports, external test
  variants, build constraints, active modules, and the package bound.
- Test reachability covers direct calls, transitive calls, methods, interface
  candidates, table-driven subtests, fuzz tests, examples, and a
  package-level fallback.
- Every uncertainty code has focused contract coverage and a meaningful near
  miss where a false-positive signal is plausible.
- `test_regex` validation and argument ordering are covered for both execution
  tools.
- All three structured-test detail modes prove complete aggregates,
  deterministic filtering, output semantics, and `tests_omitted`.
- Rule context proves active-only resource output and visible-rule-only audit
  output.
- The in-memory protocol inventory proves exactly eight tools, four resources,
  and four prompts.

### Dogfood and release matrix

Before tagging, run the stdio MCP server against agentic-go with a dirty but
known working-tree change. Require the impact explanation to identify the
changed declarations, select at least one relevant test or explicit fallback,
execute the returned plan, expose all uncertainty, use workspace-relative
locations, leave no persistent client configuration, and leave no worktree
artifacts.

Then run the repository's existing release gate: Go 1.25/1.26/1.27 tests, Go
1.27 race/vet/build, Staticcheck, golangci-lint, four-target cross-builds,
signature/history checks, and `git diff --check`.

There is no 36-run agent A/B study, token-usage benchmark, broad benchmark
program, or mandatory ten-repository analyzer rescan in v0.2.0. The pinned
v0.1.0 external analyzer evidence remains valid because no rule predicate
changes. If a predicate changes despite this scope, its focused real-project
evaluation gate is reactivated for that rule before release.

## Definition of done

v0.2.0 is ready for explicit tag approval only when:

- `docs/v0.2.0-release-scope.md` still matches the implemented wire contract;
- the live inventory is exactly eight tools, four resources, and four prompts;
- `go_change_impact` produces deterministic, contained, evidence-backed plans
  and explicit uncertainty without executing target code;
- selected tests execute through both structured test and race tools;
- v0.1.0 clients can request `detail="all"` to recover complete test records;
- analyzer context is truthful and derived from one metadata source;
- focused fixtures, MCP dogfood, and the existing release matrix pass; and
- the branch is clean, signed, locally reviewable, and neither tagged nor
  pushed without the maintainer's final confirmation.
