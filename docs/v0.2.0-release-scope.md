# v0.2.0 release scope — change verification for Go

This document is the canonical implementation authority for v0.2.0. The
tagged [`v0.1.0 release scope`](v0.1.0-release-scope.md) remains the
compatibility baseline. When this document conflicts with a roadmap or phase
document, this document wins for v0.2.0.

Read [`../CONTEXT.md`](../CONTEXT.md) for the domain language and
[`contracts.md`](contracts.md) for shared execution, containment, finding,
trace, and release invariants.

## Product contract

Agentic-go is language-native change verification for Go. Given an explicit
local base and the final working-tree snapshot, it reports:

1. what changed;
2. which workspace packages may be affected;
3. which checks were selected and why;
4. which evidence was actually collected;
5. which findings were introduced; and
6. which risks and uncertainties remain.

The verification report is the product boundary. The CLI, GitHub Action, and
MCP server are delivery adapters over one implementation. Agentic-go does not
embed an LLM, edit source, become an agent framework, or claim that a passing
report proves a change safe.

The v0.1.0 analyzer calibration remains the trust seed. v0.2.0 adds a useful
workflow around those unchanged predicates; it does not add analyzer domains
or reactivate rules disabled during calibration.

## Release inventory

v0.2.0 ships:

- `agentic-go verify` with terminal and `agentic.verify/v1alpha1` JSON output;
- one composite GitHub Action over the released `agentic-go` binary;
- eight MCP tools, including the new `go_verify_change`;
- the existing four resources and four prompts;
- the unchanged `agentic-go-vet` binary; and
- stdio as the only MCP transport.

The seven v0.1.0 tool schemas and behavior remain compatible. The existing
`verify-change` prompt changes intentionally to call `go_verify_change` once.

The previous v0.2 draft's `go_change_impact`, SSA/VTA reachability, selected
tests, `test_regex`, and structured-test detail changes do not ship.

## Module seams

The deep module has one conceptual interface:

```text
Verify(change request, policy) -> verification report
```

The implementation flow is:

```text
Change Request
  -> Change Snapshot
  -> Affected Package Closure
  -> Verification Plan
  -> Executed Evidence
  -> Verification Report
```

- `internal/verification` owns policy, orchestration, portable report types,
  deterministic assembly, and result evaluation.
- `internal/changeimpact` owns Git parsing, Go declaration mapping, active
  module/package inventory, reverse imports, and change-grounded risk facts.
- Existing `workspace`, `execution`, `parser`, `audit`, `analysis`, and
  `finding` packages remain implementation dependencies.
- CLI, GitHub, and MCP code render or transport a completed report. They do
  not independently calculate impact or reinterpret evidence.
- MCP packages and MCP tool names never appear in the verification module.

No public Go library or third-party provider interface ships. A second real
language implementation must exercise the report contract before a shared
runtime or plugin protocol is extracted.

## Portable report contract

The canonical schema identifier is `agentic.verify/v1alpha1`. The frozen
[v0.2 JSON Schema](schema/archive/verification-report-v1alpha1.json) and its Go
report type describe the same wire contract. Every
collection is non-nil and deterministically ordered.

The report contains these top-level fields in order:

```text
schema_version
provider
repository
change
impact
plan
evidence
findings
findings_total
findings_truncated
risks
uncertainties
result
```

### Provider and repository

`provider` names `agentic-go` and its binary version. `repository` contains:

- the requested base;
- the full resolved base commit;
- the full merge-base commit;
- the current full `HEAD` commit;
- a `sha256:` identity covering those commits and the final changed content;
- the slash-separated workspace path relative to the Git repository; and
- whether the final snapshot contains uncommitted content.

No absolute workspace or cache path appears in a report.

### Change and impact

`change` contains changed files and declarations. File kinds are `added`,
`modified`, `deleted`, `renamed`, and `untracked`; every file has base and
current zero-context line ranges, with `previous_path` for renames. Files,
declarations, and per-file ranges carry full totals and explicit truncation
flags when the portable report retains fewer display details than discovery
used.

Declaration kinds are `function`, `method`, `type`, `variable`, `constant`,
and `field`. A declaration records its Go package, qualified name, change
kind, and whichever base/current workspace-relative locations exist.

`impact` contains directly changed packages and their transitive reverse
importers. The complete closure drives planning and execution before portable
display details are bounded; its full count and truncation remain explicit.
Package units use `kind="go.package"`, import path as stable ID, minimum
reverse-import distance, and one or more reasons. Reasons are
`changed_source`, `embedded_file`, `module_metadata`, `workspace_metadata`,
and `reverse_import`.

### Plan and evidence

Plan check kinds are semantic, never MCP names:

- `go.test`;
- `go.coverage`;
- `go.race` when requested;
- `go.analysis.concurrency`; and
- `go.analysis.errors`.

Every check has a stable request-local ID, targets, required flag, and reason.
Target lists carry their complete count and an explicit truncation flag.
Evidence references that check ID and has status `passed`, `failed`, `skipped`,
or `error`, plus duration, summary, bounded counts, and nonpassing details.

Passing individual test records are not included. Test evidence retains
bounded package aggregates and failed/skipped test cases with full totals.
Coverage evidence contains statement-weighted totals and bounded uncovered
changed ranges. Analyzer evidence contains
base/current/introduced/resolved/unknown counts.

### Findings, risks, and uncertainties

Findings have a stable kind, severity, message, optional suggestion, source
location, check reference, and baseline state. Analyzer baseline states are
`introduced`, `existing`, `resolved`, and `unknown`; only introduced current
findings appear in the primary finding list. Test failures, race conflicts,
and an explicitly configured coverage-policy violation are findings without
an analyzer baseline state.

Risk areas are changed constructs, not diagnoses. Each risk has a stable code,
one or more source locations, a reason grounded in the snapshot, and focused
review or check guidance. Repeated locations are deduplicated, ordered, and
bounded with their full count retained. Absence of a risk trigger is never
evidence that the risk class is absent.

Uncertainties have a stable code, message, optional locations, and optional
check reference. Equal code/message/check facts are aggregated across source
locations, then bounded with their full location count retained. They state
known limits but do not automatically make the policy result incomplete.

Primary findings carry `findings_total` and `findings_truncated`. Policy is
evaluated against every finding before display truncation, so a hidden detail
cannot turn `findings` into `pass`.

### Policy result and exits

Result status is:

- `pass`: every required check completed and no policy-blocking evidence was
  observed;
- `findings`: every required check completed and blocking evidence was
  observed; or
- `incomplete`: at least one required check could not provide trustworthy
  evidence.

Precedence is `incomplete`, then `findings`, then `pass`. CLI exit codes are
`2`, `1`, and `0` respectively. `pass` is never rendered as “safe.”

Failed tests and race conflicts always block. Introduced analyzer findings
block at or above `fail_on`, whose default is `error`. Warning and info
findings remain visible. Changed coverage is advisory unless
`min_changed_coverage` is explicitly set.

## CLI contract

```sh
agentic-go verify --base origin/main
```

`agentic-go` with no positional command continues to start the v0.1-compatible
stdio MCP server. `agentic-go --version` remains unchanged.

`verify` accepts:

| Flag | Default | Contract |
|---|---:|---|
| `--base` | none | Required local commit or ref; never fetched |
| `--workspace` | `.` | Symlink-resolved Go module/workspace root |
| `--package` | `./...` | Package analysis universe |
| `--format` | `text` | `text` or `json` |
| `--race` | `false` | Include race detection in the test run |
| `--fail-on` | `error` | `error`, `warning`, `info`, or `none` |
| `--min-changed-coverage` | unset | Optional inclusive percentage in `0..100` |
| `--max-packages` | `200` | Minimum 1, maximum 500 |

Text output goes to stdout and lifecycle/input diagnostics go to stderr. JSON
mode writes exactly one report object to stdout so it can be redirected or
consumed by the Action. Infrastructure failure before a trustworthy report
uses exit 2 without fabricating an incomplete report.

No plan-only mode, low-level CLI mirrors, `doctor`, SARIF, `--go`, automatic
toolchain installation, or Windows support claim ships.

## MCP contract

The new `go_verify_change` input is:

```go
type VerifyChangeInput struct {
    Base               string   `json:"base"`
    Package            string   `json:"package,omitempty"`
    Race               bool     `json:"race,omitempty"`
    FailOn             string   `json:"fail_on,omitempty"`
    MinChangedCoverage *float64 `json:"min_changed_coverage,omitempty"`
    MaxPackages        int      `json:"max_packages,omitempty"`
}
```

Defaults match the CLI. `structuredContent` is the canonical report directly,
not a parallel MCP-only envelope. Text content is a concise status fallback
rather than a second serialization of the report, preserving coding-client
output budget while retaining the complete structured contract.

Tool annotations are read-only `false`, destructive `true`, idempotent
`false`, and open-world `true`. The description states reassuringly that it
runs the same trusted repository tests a developer would run locally, under
the MCP process's operating-system privileges and containment controls.

Invalid input, invalid Git state, containment failure, cancellation, and the
global deadline return protocol errors. Expected test failures, race findings,
analyzer findings, and individually unavailable checks return a report.

The prompt named `verify-change` requires a `base`, calls this tool once, and
explains evidence, findings, risk areas, and uncertainty without calling the
seven lower-level tools again.

## GitHub Action contract

The root composite Action is a thin released-binary adapter. It assumes the
caller already used `actions/checkout` with sufficient history and
`actions/setup-go` with a supported toolchain.

Inputs are:

- `base`: optional only for pull requests, where the event base SHA is used;
  required for other events;
- `package`: default `./...`;
- `race`: default `false`;
- `fail-on`: default `error`;
- `min-changed-coverage`: unset;
- `max-packages`: default `200`;
- `enforce`: default `false`; and
- `version`: defaults to the semver action ref and is required when the action
  is pinned by commit SHA.

The Action downloads the exact server-only archive for the runner's
Darwin/Linux amd64/arm64 target, verifies it against the release's
`checksums.txt`, and runs `agentic-go verify` once in JSON mode. It never uses
`latest`, builds another engine, installs Go, fetches the base, comments on a
pull request, or requests write permission.

It writes a concise Markdown job summary, emits source annotations for
source-located findings, stores the canonical JSON report under
`RUNNER_TEMP`, and exposes `report-path` and `status` outputs. Advisory mode
exits zero after a valid report while retaining its actual status. With
`enforce=true`, the Action propagates report exits 1 and 2.

The project release publishes separate, unambiguously named archives:

```text
agentic-go_<version>_<os>_<arch>.tar.gz
agentic-go-vet_<version>_<os>_<arch>.tar.gz
checksums.txt
```

## Change snapshot

1. Reject an empty or option-like base. Resolve it with Git end-of-options
   protection and peel it to a full commit ID.
2. Resolve `HEAD`, then calculate the merge base of the resolved base and
   `HEAD`. The merge base is the comparison tree.
3. Resolve the repository root and require it to contain the configured
   symlink-resolved workspace. A nested workspace is valid.
4. Read tracked final-state changes with rename detection and both a NUL
   delimited raw diff and matching zero-context patch from merge base to the
   working tree. This includes committed, staged, and unstaged content.
5. Add untracked, non-ignored files using Git's NUL-delimited file list. A
   tracked final path wins over a malformed duplicate.
6. Normalize every path to slash-separated workspace-relative form and reject
   traversal or a resolved path outside the workspace.
7. Read base content from Git and current content from the final workspace.
   Reject malformed Git output rather than returning a partial snapshot.
8. Recompute a bounded final-state fingerprint after discovery. If relevant
   paths changed during analysis, return an error instead of combining two
   repository states.

Changed declarations are parsed from base/current Go syntax and are included
only when their source span intersects a changed hunk. Methods include their
receiver identity. Deleted declarations use base package metadata; added and
untracked declarations use current metadata.

Generated files are analyzed but produce `generated_code`. Active build-tag
files describe only the current toolchain configuration. Ignored tagged files,
cgo, assembly, plugins, generated-at-build source, and external consumers are
limitations or uncertainty, never silently modeled claims.

## Affected package closure

Enumerate the selected package universe once per active module in a Go
workspace, or from the containing module otherwise. Collect current package,
module, file, embed, import, test, cgo, and ignored-file metadata with
`GOWORK=auto`, `GOTOOLCHAIN=local`, and `-mod=readonly`.

Direct packages are selected by:

- a changed active Go or test file;
- a changed file listed by active `EmbedFiles` or `TestEmbedFiles`;
- a relevant `go.mod` or `go.sum`, which selects its module; or
- `go.work` or `go.work.sum`, which selects the active workspace.

Do not reimplement embed glob matching. Deleted paths use the base inventory
when the current inventory cannot identify them.

Build a reverse import graph over contained packages and breadth-first add all
transitive importers, preserving minimum distance. External dependencies and
packages outside the configured scope are not executed; exported changes
produce `external_consumers` uncertainty.

If the closure exceeds `max_packages`, return an incomplete report containing
the observed count and narrowing guidance. Never execute or imply confidence
in a nearest-package prefix. A clean non-Go/documentation-only change may
produce a complete report with no planned checks; unmodeled build/generator
inputs remain explicit uncertainty.

## Evidence execution

The current-snapshot test and coverage check is one bounded command over
explicit affected package import paths:

```text
go test -json -timeout 60s -covermode=atomic \
  -coverprofile=<run-dir>/coverage.out \
  -coverpkg=<direct-current-packages> \
  <affected-packages...>
```

Add `-race` when requested. When no current executable Go statement changed,
omit coverage flags and record coverage as skipped/not applicable rather than
zero. A non-zero test exit is evidence, not an infrastructure error.

Test evidence streams events, retains aggregates and nonpassing records, and
preserves package-level `skip` for packages without tests. Coverage profiles
are size-bounded, path-contained, and statement-weighted. A coverage block is
changed when its current source range intersects an added or modified hunk;
the whole block's statement count participates. Deleted code has no current
coverage and is reported as uncertainty, not zero-covered statements.

Run the unchanged concurrency and error analyzers over affected packages in
both the current snapshot and a base snapshot. Base files are extracted from
the merge-base tree into a traversal-safe temporary directory under
`os.UserCacheDir()/agentic-go/runs/...`; do not create a Git worktree or mutate
target Git metadata. Remove temporary source and raw profiles on every normal
return.

Static audit package loading remains closed-world (`GOPROXY=off`,
`GOSUMDB=off`, `GOTOOLCHAIN=local`). Test execution follows the caller's Go
module proxy/checksum policy and may obtain missing modules exactly as a direct
`go test` would; agentic-go itself performs no hosted analysis or telemetry.

Independent checks continue after a test failure, coverage parse failure, or
one audit failure. A check error marks required evidence incomplete. Request
cancellation and the whole-verification deadline stop immediately.

## Analyzer baseline comparison

Use the Git rename map and unchanged-line mapping from the zero-context patch.
A current diagnostic is `existing` only when a base diagnostic with the same
rule and normalized message maps to that exact unchanged source location.

- unmatched current diagnostics are `introduced`;
- unmatched base diagnostics are `resolved`;
- a changed or ambiguously mapped location is `unknown` and produces
  `baseline_unknown` uncertainty; and
- unknown diagnostics never block or masquerade as introduced.

If the base audit cannot run, current diagnostics remain available as evidence
but no introduced claim is made; the analyzer check is incomplete. The report
does not use semantic fingerprints across modified declarations in v0.2.0.

## Change-grounded risk areas

Risk detection is limited to source constructs intersecting changed hunks:

- `public_api_changed`: exported declaration added, changed, deleted, or
  renamed; activates API-design and naming/maintainability review;
- `module_graph_changed`: module/workspace metadata changed; activates
  security and supply-chain review;
- `concurrency_construct_changed`: goroutine, channel, select, synchronization,
  atomic, context, timer, or ticker construct changed; recommends race evidence
  when it was not requested;
- `error_flow_changed`: error-typed return, wrapping/inspection, ignored error,
  panic, fatal, or process exit changed; activates error and observability
  review;
- `external_boundary_changed`: HTTP, database, crypto, serialization, regular
  expression, environment, or filesystem boundary changed; activates security
  and observability review;
- `instrumentation_changed`: logging, tracing, or metrics call changed;
  activates observability review; and
- `performance_sensitive_construct_changed`: loop, allocation, reflection,
  formatting, writer, or benchmark construct changed; activates performance
  review.

Detection records the exact construct and location. It does not execute or
relabel the deferred security, observability, naming, type-design, or
performance rule catalogs. Risk areas never affect the policy result directly.

## Bounds and trust boundary

Defaults and fixed limits are:

- 500 changed files, configurable only by package scope;
- 200 affected packages, configurable from 1 through 500;
- 10,000 active or changed-base Go files;
- 64 MiB combined current/base source;
- 15 visible changed files with full counts;
- 5 visible base and current ranges per changed file with full counts;
- 20 visible changed declarations and 20 impacted packages with full counts;
- 20 visible targets per planned check with full counts;
- 20 visible test-package summaries and 20 nonpassing test cases with full
  counts;
- 50 visible primary findings with full pre-truncation counts;
- 20 visible changed coverage ranges with full counts;
- 5 visible locations per risk or uncertainty with full counts;
- 8 MiB per subprocess stdout and stderr stream;
- four concurrent Go/Git operations; and
- a 300-second whole-verification deadline.

Crossing a source or package bound before a trustworthy plan yields
`incomplete`; truncating nonblocking display details is explicit and cannot
turn findings into pass.

All subprocesses use argument arrays, request-derived contexts, shared
concurrency, deadlines, process-tree cancellation, bounded output, and
contained working directories. Agentic-go executes trusted target repository
tests with the caller's operating-system privileges. These controls are
containment, not sandboxing.

## Focused acceptance contract

Tests are written through the change-impact, verification-report, verifier,
CLI, MCP, and Action seams. Required scenarios include:

- added, modified, deleted, renamed, staged, unstaged, and untracked files;
- a workspace nested in a repository and a multi-module `go.work`;
- declaration changes, reverse import distances, embeds, metadata, generated
  files, build constraints, cgo, and graph overflow;
- changed executable statements covered by direct and reverse-importer tests,
  uncovered statements, no-test packages, and an explicit coverage threshold;
- baseline matches after shifted lines and renames, introduced/resolved
  findings, ambiguous mappings, and an unavailable base audit;
- every risk trigger plus a meaningful near miss;
- deterministic non-nil report collections and result precedence;
- independent-check continuation, cancellation, deadline, output caps,
  cache cleanup, and workspace containment;
- CLI text/JSON rendering and exits 0/1/2 while no-command MCP startup remains;
- exactly eight MCP tools, four resources, and four prompts with truthful
  `go_verify_change` annotations; and
- Action checksum rejection, platform mapping, PR/manual base behavior,
  summary/annotations, outputs, and advisory/enforced exits.

Before release approval:

1. dogfood CLI and ephemeral stdio MCP verification against agentic-go;
2. record three reviewed reports from already-cloned repositories covering
   reverse impact, changed coverage, and analyzer baselining;
3. run tests on Go 1.25, 1.26, and 1.27;
4. run Go 1.27 race, vet, build, Staticcheck, and golangci-lint;
5. cross-build both binaries for Darwin/Linux amd64/arm64;
6. verify signatures, history, release configuration, and `git diff --check`;
   and
7. require a clean worktree with no persistent MCP client configuration.

There is no agent A/B study, design-partner requirement, token benchmark,
broad benchmark program, or mandatory ten-repository analyzer rescan. Any
analyzer predicate change reactivates that rule's focused external-calibration
gate.

## Explicitly deferred

- selected tests, test reachability, SSA, VTA, and public test maps;
- new analyzer domains or changed predicates;
- SARIF, doctor, automatic toolchain installation, or a `--go` flag;
- HTTP/SSE, sessions, background polling, or hosted analysis;
- autonomous fixes or source mutation;
- a plugin ABI or shared cross-language runtime;
- unsupported Windows claims; and
- the `github.com/agentic-mcps/go` module migration.
