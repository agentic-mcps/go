# v0.8.0 evaluation scope

## Purpose

v0.8 establishes a reproducible evaluation system for the v1 intelligence
workflow. It does not add production MCP tools or make claims about model
accuracy, token savings, or adoption.

The corpus answers four separate questions:

1. Did a candidate change satisfy upstream behavioral checks?
2. Did it stay within the task's declared structural scope?
3. What source-grounded MCP evidence did each server mode return?
4. What did that evidence cost in serialized result bytes, calls, and time?

Passing these checks is evidence for one pinned task. It is not proof that an
implementation is equivalent to the historical upstream patch.

## Corpus contract

The canonical corpus contains eight historical Go tasks. Each manifest pins a
repository URL, parent commit, target commit, human task prompt, permitted
paths, upstream oracle files, acceptance commands, and expected invariants.
The parent and target must be adjacent commits.

The checked-in repository contains manifests, schemas, and recorded results.
It does not vendor third-party source or Git objects. The evaluation runner
prepares content-addressed Git bundles from caller-supplied local clones and
stores them outside this worktree. Preparation verifies both upstream commits
and the target's exact parent before copying either snapshot.

Prepared bundles contain a deterministic two-commit fixture history. The
fixture commits are explicitly identified as locally synthesized evaluation
snapshots and retain the upstream commit IDs in their messages. They do not
claim to reproduce upstream authorship, dates, reviews, or intervening history.

Setup checks out only the fixture base branch. The target branch remains in the
private bundle so the scorer can overlay upstream regression tests into an
isolated scoring clone. A model is never scored by exact patch equality.

## Scoring

The scorer observes the candidate relative to its fixture base, including
staged, unstaged, and untracked files. It fails scope safety when any changed
path is outside the manifest's permitted paths.

Correctness commands run in a temporary clone containing the candidate change
plus the target versions of declared oracle files. This preserves alternative
production implementations while evaluating them with the historical
regression tests. Commands are argv arrays, never shell strings. They run with:

- `GOTOOLCHAIN=local`;
- `GOPROXY=off` and `GOSUMDB=off`;
- a manifest timeout;
- bounded stdout and stderr;
- the caller's existing module cache and privileges.

An absent dependency is `incomplete`, not a failed solution. A non-zero test
exit is `fail`. Result precedence is `incomplete`, then `fail`, then `pass`.

## MCP replay and measurement

A replay transcript contains literal MCP tool calls and expected transport
outcomes. The runner starts one stdio server in the task workspace, invokes
calls in order, writes content-addressed response artifacts, and records:

- tool call count;
- serialized MCP result bytes;
- per-call and total duration;
- transport or expectation failures.

Result bytes are the context-cost measure. Model-token counts remain absent
unless a real client supplies them reliably. Replay measures deterministic
server behavior, not whether a coding model would produce a correct patch.

Cached native-tool and upstream-gopls baselines must record their exact command
or server version. A baseline is evidence from that mode, not an equivalent MCP
contract.

## Pilot boundary

Two manifests are marked for the bounded paid pilot:

```text
2 tasks x 2 clients x 3 modes = 12 runs
```

The clients are Codex and Claude Code. The modes are native client tools,
upstream gopls MCP, and agentic-go. Starting those paid runs requires explicit
authorization and available clients. The remaining six tasks use deterministic
server replay only.

Documentation may claim reduced context cost or fewer model mistakes only if
the recorded pilot supports that exact claim. Otherwise v1 ships deterministic
contracts without the claim.

## Release gate

v0.8 is complete when:

- all eight manifests validate and their pinned adjacent commits are available;
- every bundle can be prepared twice with the same SHA-256 digest;
- every base workspace can be set up without network access;
- the historical target passes its own scorer;
- a no-op candidate fails every task scorer;
- every behavioral oracle fails on the fixture base and passes on the
  historical reference change;
- out-of-scope edits fail independently while the behavioral oracle still
  passes;
- replay results and cached artifacts contain no absolute local paths;
- the standard supported-toolchain matrix remains clean.

No tag, push, transfer, paid pilot, or public model-performance claim is part of
this implementation slice.
